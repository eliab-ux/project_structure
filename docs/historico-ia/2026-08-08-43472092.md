## O que a frase quer dizer

É o **painel de saúde** classificando o chip. O texto vem de [get-health-panel.use-case.ts:152](apps/batuta-system/backend/src/contexts/audit/application/use-cases/get-health-panel/get-health-panel.use-case.ts#L152), no método `assess()`, que reduz cinco métricas a uma palavra por chip. Esse ramo dispara quando `deliveryRate < 0.85` e marca o canal como **AT_RISK**.

A leitura pretendida é: *"o WhatsApp nunca te avisa que um número foi bloqueado; quando as mensagens saem mas não são entregues, isso é o sinal indireto de bloqueio"*. Daí a frase "perfil de número sendo bloqueado".

## Mas 0% exato não é bloqueio — é contador que nunca foi alimentado

Bloqueio real produz entrega **degradada** (30%, 60%), não zero absoluto. Zero com envios > 0 significa que o numerador nunca foi preenchido. E é exatamente o que o código faz hoje:

`deliveryRate = delivered / sent`, somando `delivered_count` dos `channel_quality_snapshots` ([audit-query.repository.ts:418](apps/batuta-system/backend/src/infrastructure/persistence/mikro-orm/repositories/audit-query.repository.ts#L418)). E quem escreve esse snapshot é [review-channel-quota.use-case.ts:104-112](apps/batuta-system/backend/src/contexts/channel/application/use-cases/review-channel-quota/review-channel-quota.use-case.ts#L104-L112), a partir de `signals.forDate(...)` — cuja única implementação, [channel-signals.repository.ts:248-256](apps/batuta-system/backend/src/infrastructure/persistence/mikro-orm/repositories/channel-signals.repository.ts#L248-L256), devolve:

```ts
sentCount: (counter?.campaignSends ?? 0) + (counter?.replySends ?? 0),
failedCount: 0,      // ← literal
deliveredCount: 0,   // ← literal
optOutCount: 0,
inboundCount: 0,
```

Ou seja: `sent_count` é real, `delivered_count` é **zero fixo, por construção**. O `delivery_status` que o webhook grava em `dispatches` é lido só por relatório e trilha de auditoria — **ninguém o agrega de volta para `delivered_count`**. O comentário no próprio port previu isso, em [channel-signals.port.ts:16-18](apps/batuta-system/backend/src/contexts/channel/application/ports/output/channel-signals.port.ts#L16-L18):

O aviso não foi cumprido. É esse o alarme na sua tela.

## Isso não é cosmético — está estrangulando a cota

O mesmo número alimenta o throttle. Em [throttle-policy.ts:163](apps/batuta-system/backend/src/contexts/channel/domain/services/throttle-policy.ts#L163), entrega abaixo de 85% → decisão **LOWER**, com `lowerFactor` 0.5 (corta a cota pela metade). E pior, em `isCleanDay()` ([linha 227](apps/batuta-system/backend/src/contexts/channel/domain/services/throttle-policy.ts#L227)) um dia com 0% de entrega **nunca** é "limpo" — então **RAISE é inalcançável** e o chip fica travado no piso de 20/dia (16 de campanha) para sempre.

O que segura isso hoje é uma só coisa: `minSampleForDecision = 20` ([throttle.config.ts:42](apps/batuta-system/backend/src/config/throttle.config.ts#L42)). Enquanto o total de envios na janela de 3 dias for menor que 20, o throttle responde HOLD ("amostra insuficiente") e não corta nada. **Passando de 20 envios em 3 dias, o corte começa.** Você está vendo o alarme antes do dano porque o painel *não tem* essa mesma guarda — `assess()` só checa `deliveryRate !== null`, então grita AT_RISK com 1 envio e 0 acks.

## O que o botão Webhook passa a responder

**Recusas por token inválido.** Aqui estava o furo mais incômodo: o check do cabeçalho só vê presença, nunca o valor — e isso é do desenho, porque comparar o esperado significaria devolver o segredo na resposta.
